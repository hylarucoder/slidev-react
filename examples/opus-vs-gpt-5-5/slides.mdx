<EditorialSlide brand="任务五 · 日常使用" eyebrow="Daily Workflow" footer="Two-step plan + todo">
  <EdH2>我的日常开发方式：文档驱动 + 两步 plan + 一步 todo</EdH2>
  <EdLede>
    在 10 万行级仓库中，所有模型都会有一定程度的幻觉（包括 Claude 和 GPT）。以下是我用来规避幻觉的工作流。
  </EdLede>

  <EdGrid cols={3} gap="32px" marginTop="48px">
    <EdCard title="Step 1 · 粗粒度 Plan" dot="var(--ed-teal-title)">
      配好 harness 环境后，先让 coding agent 与代码库对话，产出一份粗粒度的执行计划，写入 docs/exec-plans/xxxx.md。这一步市面上几乎所有大模型都会有幻觉。产出后<b>人工扫一眼</b>，确认是否符合自己对代码的认识。
    </EdCard>
    <EdCard title="Step 2 · 细化 Plan" dot="var(--ed-coral-title)">
      不让模型直接执行，而是要求它<b>再细化一轮</b>。细化后幻觉概率明显降低——模型被迫重新审视自己的计划。同样经过<b>人工审核</b>后再进入下一步。
    </EdCard>
    <EdCard title="Step 3 · 拆解 Todo" dot="var(--ed-amber-title)">
      让模型结合实际代码，把细化后的 plan 拆解成具体的 todo。每个 todo 对应到真实的文件和函数，再次<b>人工确认</b>后才开始执行。
    </EdCard>
  </EdGrid>

  <EdInsight label="核心思路">
    每一步都有人作为审核环节。目前大部分模型的 coding 本身没问题，问题出在<b>架构把握和幻觉</b>上。通过<b>粗 plan → 细化 → todo</b> 的递进结构加人工审核，幻觉被逐层过滤。
  </EdInsight>
</EditorialSlide>

  <EdH2 size="sm">两种模型，两种气质</EdH2>

  <EdNumList>
    <EdNumItem>
      <div><b>纵深 vs 效率。</b>　Opus 是洞察型——深挖、链路追踪、异常分析拉满（9 分），规划和遵从度扎实（8-9 分），但迭代速度偏慢（6 分）。GPT-5.5 是效率型——迭代快（9 分）、视觉设计好（8 分），但深挖和规范性不如 Opus。</div>

      <div><b>选 Opus。</b>　需要穿针引线深挖代码链路、做架构尽调、长程工程任务、从零构建复杂项目（如 Python 解释器），或者需要精准的异常分析和技术文档。</div>
